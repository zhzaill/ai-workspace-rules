# AI 工作区快速复刻手册

> 这是一份导航层文档，用于让新的 AI 会话快速理解一个受规则管理的工作区。它不替代项目自身的 `AGENTS.md`、`README.md` 或安全策略；冲突时以任务专属规则为准。

## 1. 首轮读取顺序

按以下顺序读取，先建立边界，再处理具体任务：

1. 工作区根目录的总入口（通常是 `AGENTS.md`）：总规则、目录职责和禁止事项。
2. 结构说明：标准目录的用途和例外目录。
3. 工作区规则：文件归类、仓库安全、不可移动对象。
4. 通用日志规则：日志位置、命名和结构。
5. 如果任务属于某个领域（例如部署、数据、媒体或硬件），读取该领域工作区的专属入口。
6. 如果任务属于具体项目或仓库，读取目标目录下的项目规则、README 和当前状态。

不要把整个磁盘的 Markdown 都当成规则。依赖包、第三方源码和生成目录里的 README 通常只是其自身说明；只有当前任务路径上的入口和专属规则具有约束力。

## 2. 工作区的基本模型

工作区不是单一项目仓库，而是按用途分流的容器。推荐使用以下职责；已有目录应尊重其现状，不因名称相似而擅自搬迁：

| 目录 | 用途 | 默认动作 |
|---|---|---|
| `data/` | 模型、数据集、下载、资产和其他大文件 | 放置不可提交或难以重建的数据 |
| `projects/` | 项目组和非仓库项目 | 组织项目工作区 |
| `repos/` | 顶层 Git 仓库 | 一个目录对应一个主仓库 |
| `tools/` | 便携工具、运行时和安装包 | 优先复用已有工具链 |
| `archive/` | 历史材料、旧安装包和退役输入 | 归档，不作为当前输入 |
| `backup/` | 补丁、bundle、配置和安全导出 | 破坏性操作前先检查 |
| `inbox/` | 尚未分类的散文件 | 先收集，再分类 |
| `meta/` | 规则、索引、状态和维护报告 | 更新工作区事实 |
| `logs/` | 通用主题的工作日志 | 按日期和主题追加 |

领域工作区可以拥有自己的入口、状态、配方和日志目录；它应明确说明与通用日志目录的分流关系。

## 3. 每个任务的执行协议

### 开始前

- 明确任务类型：工作区维护、项目/仓库、还是领域专属工作流。
- 读取对应入口和最近状态；先看当前状态，再看历史日志。
- 检查目标路径是否已有文件、是否位于 Git 仓库、是否存在并行作业或未提交修改。
- 只把已验证内容当事实；推测必须标记，并写出验证方法。

### 执行中

- 新建散文件先放 `inbox/`，确认归属后再分类；历史材料放 `archive/`，备份放 `backup/`。
- 不在仓库中放模型、缓存、构建输出、下载物和密钥。
- 不移动或删除规则中列出的受保护对象。
- 仓库有无远端或未提交修改时，不物理移动；先提交或做备份。
- 不覆盖并行作业；发现他人改动时只增不删，日志追加而不是重写。
- 遵守当前操作系统的编码和脚本版本约束，命令必须可直接复制执行。

### 完成后

- 验证产物、路径、大小、状态和退出结果；“文件存在”不等于操作成功。
- 新增事实写入对应分册；新增通用故障写入故障手册；状态变化更新状态快照。
- 写一条日志；同一天同主题追加，不新建第二条。
- 日志只写可复现证据，不写凭据或秘密。

## 4. Git 与文件安全

为每个仓库维护一个可更新的索引。至少区分：

- `NO_ORIGIN`：没有远端，移动前必须备份。
- `DIRTY`：有未提交修改，保持原位直到清理或备份。
- `CLEAN_REMOTE`：有远端且工作树干净。

处理仓库前至少确认：

```powershell
git -C "目标仓库绝对路径" status --short --branch
git -C "目标仓库绝对路径" remote -v
```

不要使用破坏性命令覆盖用户修改。交付或归档使用白名单（例如 `git archive`）优先于对整个目录打包；模型、虚拟环境、依赖目录、构建目录、密钥和真实数据按项目规则处理。

## 5. 下载、安装和外部变更的闭环

凡是下载或安装大文件：

1. 记录来源和来源声明大小。
2. 落盘后读取本地字节数。
3. 与来源 `Content-Length` 或等价的完整性声明逐字节比较。
4. 不相等就标记失败或未完成，不以“文件存在”作为成功依据。

凡是会修改远程机器、服务配置、凭据相关配置或第三方文件的操作：先读专属规则并备份；完成后重新读取或探测，确认实际状态。

## 6. 日志最小模板

普通主题使用 `logs/YYYY-MM-DD-<topic>.md`；领域工作流可以使用自己的日志目录，但必须声明分流规则。

```markdown
# YYYY-MM-DD · <topic>

## 做了什么
1. <动词开头，一条一件事>

## 结论
<可复用判断；写清因为 A 所以 B>

## 证据
- 命令：`<可直接复制的命令>`
- 路径：`<绝对路径或仓库内路径>`
- 实测数字：<字节数、耗时、端口、退出码等>

## 未决项
- <待验证、待用户决定或有风险的事项>
```

日志纪律：四段不可缺；事实与推测分开；不写密码、令牌或私有地址；不删除旧判断，结论变化用“更正”追加；产物路径要能被下一轮直接使用。

## 7. 领域专属工作区

领域工作流可以在自己的目录提供一份 `AGENTS.md`，内容至少包括：

- 唯一入口和索引
- 不可违反的边界
- 环境、工具和访问方式
- 常见故障与可复制配方
- 当前状态、未决项和并行作业说明
- 专属日志位置和写法

领域入口只记录经过验证的事实。凭据放在受控的访问配置中，不复制进日志、README 或公开仓库。

## 8. 给新 AI 的可复制首轮提示

```text
你在一个受规则管理的 AI 工作区工作。先读工作区根目录的 AGENTS.md、结构说明、workspace-rules 和日志规则；根据任务类型再读目标目录的专属入口、README 和当前状态。
只把已验证内容当事实，推测要标注并给验证方法。先检查现状、Git 状态、并行作业和目标路径，再执行修改。
新散文件进 inbox，历史材料进 archive，备份进 backup；仓库中的模型、缓存、构建输出、下载物和密钥不入库。
任何下载或安装都要用来源声明与本地字节数闭环验证。任何任务结束都要更新对应状态或分册，并按日志规则写一条四段日志；日志不写凭据、令牌或私有地址，产物路径必须可复现。
```

## 9. 发布前脱敏检查

将规则手册发布到公开仓库前，逐项检查：

- 删除本机绝对路径、用户名、主机名、内网 IP、MAC 地址和端口组合。
- 删除密码、令牌、私钥、访问配置路径和命令行凭据。
- 删除个人姓名、角色名、私有项目名、内部日志和服务器状态。
- 将具体目录替换成通用目录名或占位符。
- 检查 Markdown、脚本、示例输出和 Git 历史，不只检查当前文件。
- 只提交可公开复用的规则、模板和示例。
